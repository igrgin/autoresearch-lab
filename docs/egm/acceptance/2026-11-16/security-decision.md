Use an application-owned credential service, macOS Keychain-backed encrypted storage, operation-scoped adapter access, and one safe-record admission policy for local and remote records. Dedicated credential-entry UI necessarily sees a newly entered value until submission; ordinary views receive only an opaque reference, user label, category, status, and safe scope metadata. Neither a label nor a reference grants access. The remote provider/service that validates a credential is its intended authentication recipient, not an application reader.

### 2. Local storage and access mechanism

Select Electron **asynchronous `safeStorage` encryption backed by macOS Keychain**, with ciphertext in an application-private vault outside all project folders and repositories. The Electron main process hosts the small secret-storage bridge because `safeStorage` is a main-process API; #15's utility-process coordinator remains the sole writer of registry/project databases. Those databases contain credential references and safe status/scope metadata only, not ciphertext or plaintext credential values. The main bridge must not become a general shell, HTTP proxy, or database interface.

Electron documents Keychain protection on macOS, the importance of consistent signing for access across updates, and platform-dependent protection/fallbacks. Its current asynchronous APIs also expose availability handling. **Decision:** key-store lock, denied consent, encryption failure or unavailable support produces an actionable authentication/storage error; never fall back to plaintext, `basic_text`, `auto` auth-file storage, an `.env`, or a second copy of the key. Qualify the selected Electron version and signed package in #18/#21 before relying on this. Future platforms need their own equivalent protection check. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).

Credential registration/replacement uses a dedicated local entry surface and validated sender-specific IPC; suppress request-body logging and clear the input after acknowledgment. The ordinary renderer cannot read back stored values. Use #15's context isolation, sandbox, disabled renderer Node access and narrow preload boundary; render captured content as untrusted text. A renderer or preload compromise is not solved by encryption at rest. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security).

The credential service authorizes the actual application component identity plus provider/account, operation purpose and resource/action scope. Do not trust a model-supplied `component`, path, URL, or credential reference as authorization. Prefer executing a narrow operation inside the adapter; where an SDK must receive plaintext, deliver it through private process IPC or the category-specific channel above, with lifetime limited to that authenticated worker. No public `getSecret`, arbitrary destination, or reusable capability is exposed to tools. Reject unknown references, wrong category/account, revoked credentials and cross-run misuse before dispatch, with #16's safe `permission_denied`/`authentication_required` error and effect certainty. Credential rotation preserves canonical provider/resource identity and reservations.

All child environments start from explicit safe allowlists, never `{...process.env}`. Candidate/helper subprocesses inherit neither the Claude worker's API key nor provider, SSH, Hub, proxy, or control credentials. Deny credential/state directories, parent-process inspection, signing sockets and credential-service IPC to untrusted code. A separate directory or same-user subprocess alone is not an enforced boundary. Local command sandbox qualification follows #44/#49; [#54](https://github.com/igrgin/autoresearch-lab/issues/54) owns concrete local/remote isolation and remote enforcement. This spike provides the required access invariant, not a selected container/UID/seccomp protocol.

Keep plaintext lifetimes short, release buffers and terminate authenticated workers when access is revoked; do not promise reliable zeroization of every JavaScript string, swap page or crash dump. Disable app-managed raw crash/heap/network dumps and automatic diagnostic uploads for credential-bearing processes. Vault and SDK-private state are excluded from project export, Git, model packages, routine support bundles and application project backups. Moving a project carries safe references with an explicit “reauthentication required” state, never portable credentials. OS/user backups may still contain sensitive machine state; account revocation, not deletion alone, contains that residual exposure.

### 3. Safe-record admission, coverage and native state

Apply the same versioned admission policy **before** a payload enters local/remote disk spools, SQLite/WAL, activity files, UI/notifications, search indexes, exports, telemetry, or agent context. Brokered tool returns must be filtered **before they are sent to the model/SDK**, as well as before application capture. Recheck retained/context records on reuse against current revocations and policy; prior admission is not permanent trust.

* **Exclude by construction:** auth RPCs, HTTP authorization/cookie headers, login/challenge replies, secret input fields, credential files, raw environment dumps and raw provider/SDK request-response objects never enter ordinary capture. Project provider responses into allowlisted IDs, state, capability and connection descriptors; keep live connection handles out of serialized #16 records. Send credentials only to validated intended origins; do not forward authorization on arbitrary redirects, model-supplied URLs, or uncontrolled proxy/config overrides.
* **Sanitize admitted content:** validate schemas/types, recursively scrub credential-designated fields, URL userinfo and secret query values, private-key blocks and recognizable token forms; match registered current/recently retired secrets and their supported escaped/URL-encoded representations. Include prompts, assistant prose, command text/argv/cwd, stdout/stderr, tool arguments/results, vendor errors/stack traces, file names/content/diffs, Git messages, attachments and inherited summaries. Even an “error,” metric label, path or model metadata string can carry a secret. Never preserve a secret prefix/suffix or publish a hash of the value. Use a neutral marker such as `[REDACTED:credential]` plus safe omission metadata.
* **Bound streaming before disclosure:** decode/reassemble bounded complete records or hold sufficient pending data for the supported matching scheme before emitting any delta. Preserve parser/matcher state across chunk boundaries, including UTF-8 and escape boundaries. Register generated secrets with the sanitizer before using them. If completion, encoding, size, nesting or safe filtering cannot be established, omit the entire unsafe body with a reason; never release an unexamined prefix or raw “debug fallback.” Binary/opaque attachments require a supported safe projection or are withheld. Scan before #86's head/tail retention cuts so fragments do not evade filtering; do not change its byte/queue limits.
* **Fail safely:** redaction omission preserves a safe #16 envelope with action/event identity, source, status, policy revision and known/unknown coverage. A broken sanitizer or unsafe collector stops admission and fences new affected agent actions/experiments; drain/discard verbose bytes in bounded memory without blocking supervision. Required outcomes/controls use separately validated safe structured records, never a raw fallback. Apply #73's bounded pause/reconciliation policy; do not relabel collection failure as execution failure, release an uncertain reservation, or stop a provider instance. Required semantic fields that cannot be safely recorded block the dependent publication instead of silently changing their meaning.

Use a second explicit **agent-context projection**: only authorized task/code/validation/constraint/acceptance records, with no credential values, raw native transcripts, or separate test assessments. Sanitizing secrets does not make user-only test data agent-safe. Rebuild later-run context from admitted application records; do not inherit arbitrary host instructions, SDK history, summaries, files or cached prompts.

Respect the different native histories already selected. Codex uses app-private persistent state for evidence inspection under #44; restrict it to the trusted adapter, exclude it from normal backup/export/context, and treat it as potentially sensitive, not as a sanitized application archive. Its auth is ephemeral, but its conversation rollouts are a separate persistence surface. Claude uses `persistSession: false`, isolated state/temp directories, and fresh-session recovery from safe app records under #49. The [Claude session docs](https://code.claude.com/docs/en/agent-sdk/sessions) confirm that disabling persistence forfeits disk-session resume; incidental diagnostics still need qualification. [Codex authentication](https://learn.chatgpt.com/docs/auth#credential-storage) distinguishes ephemeral memory from `auth.json` storage.

Sanitizing an App Server activity event **after** a built-in tool has already supplied raw output to its model/native rollout cannot undo that exposure. Credential-bearing operations must use the trusted broker, and direct tools must have no credential-bearing sources. If an integration bypasses pre-model/pre-persistence filtering, that path cannot be used for secret-bearing work. Contaminate/retire the session on discovery; never claim a cleaned UI makes the native session safe. Unknown or deliberately transformed secrets cannot be perfectly recognized: isolation, restricted sources/tools, known-value matching and conservative omission reduce exposure; they do not constitute a universal detector.

### 4. End-to-end trace: secret-bearing download result

The identifiers below are illustrative, not a live operation; no credential value is included.

1. Setup action `action_setup` requests an approved model/revision via a scoped tool. The trusted coordinator binds `operation_fetch` and `credential_ref_hub` out of band; the agent does not choose an arbitrary URL or receive the reference's value. A candidate command containing an embedded token is rejected/sanitized at ingress, not executed and merely hidden afterward.
2. Trusted fetcher resolves that reference and authenticates over HTTPS. It does not construct a shell command containing a token. Any internal response/error containing a token or signed URL stays in bounded trusted memory; no raw request logging, shell tracing, spool, or debug cURL rendering is enabled. Filter the result before returning it to the tool/model and before emitting its application event.
3. Persist an admitted #16 event for `operation_fetch` with safe source/revision, artifact reference, terminal status or safe `permission_denied`/`authentication_required` error, and `redacted`/`omitted` coverage. No auth headers, URL query, response dump or token-bearing preview reaches SQL/WAL/activity files or the remote spool. Store content/revision identity rather than a signed download URL. Apply #86 quotas only to sanitized detail.
4. UI and notifications display that same safe projection and an explicit omission marker when detail was withheld. Export/search/debug bundles use admitted records, not the fetcher's raw buffer. Trusted preparation transfers the fixed credential-free artifact; the remote trainer gets files and a clean environment, not the fetcher's token/cache.
5. A later research action or run receives only the authorized safe result through the context builder, after current-policy/revocation checks and test-assessment exclusion. Never recover context from the fetcher's private cache or a native raw transcript. If the original return reached a model before filtering, use the exposure process below and a fresh session; this trace cannot retroactively certify it safe.

### 5. Accidental emission and containment

Treat a registered credential appearing in a prohibited destination, a suspected unrecognized credential, or an unsafe raw capture as an incident. A match removed inside the trusted admission buffer can be recorded as **prevented**; a record/model/native-history destination already receiving it is **exposed**, even if UI display was subsequently cleaned. Unknown reach remains unknown. Neither case copies the value into incident reports.

1. **Fence propagation immediately.** Deny affected payload/event IDs across read projections, exports, indexing, replay, agent-context construction and new actions. Disable ordinary use of the affected credential reference and stop new affected work. Retire any contaminated agent session and fence its tools; bounded cancellation/reconciliation follows the integration/#73 policy. Other safety controls remain available through uncompromised channels. Remote unknown work retains its reservation; loss of credentials is not proof of stop.
2. **Report by identity only.** Record `incident_id`, project/run/action/operation/record references, credential category and opaque ID when known, detected time, suspected destinations, prevented/exposed/unknown reach, safe reason, policy version, remediation state and coverage gaps. Example: “A model-download credential may have reached agent activity. Affected records are withheld. Replace the credential before resuming.” No value, partial value, surrounding excerpt, raw screenshot, token-derived hash, or raw diagnostic attachment appears in the UI, issue, log, notification or next agent prompt.
3. **Contain existing copies.** Quarantine affected app/native/remote records **in place**, revoke normal access and prevent replay; do not create a new raw evidence archive. Rescan linked transcripts, summaries/compactions, caches, files/diffs/Git objects, exports and context descendants through the trusted sanitizer. If a source cannot be safely inspected, withhold the whole affected source/session and record incomplete coverage. Publish redacted replacement/correction records with their own identities and a reference to the withheld original. Preserve #16's domain identities/provenance and a safe tombstone; do not reuse an event ID with different bytes or pretend immutable raw evidence can stay generally readable. Remove contaminated app-controlled payload copies when safe replacement is established, including derived indexes/temporary copies; report inaccessible remote copies or user exports/backups as unresolved. SQLite WAL/free pages, snapshots and external backups may retain bytes despite logical deletion; remediation must account for them without claiming forensic erasure. Repository review archives are not incident scratch space and remain unchanged by this task.
4. **Invalidate the authority.** Prompt the user through trusted credential settings to revoke/rotate the affected provider/API/model credential or SSH identity in its issuing service and replace the reference. App-owned control capabilities can be invalidated locally/remotely within the chosen protocol. Do not silently rotate account keys, change provider lifecycle, or register SSH keys. For externally injected credentials, report the required provider-side repair and keep the route unavailable if isolation/containment cannot be established. A retired value may be retained only in protected remediation matching state while rescanning; it is not usable for authentication and is removed after remediation. If a model service already received the value, rotation is required; deleting local records cannot retract the remote context.
5. **Recover deliberately.** Verify replacement access and the access/recording boundary; reconcile existing operation effects before resending anything. Start a fresh agent session from accepted/initial code and independently admitted history, not a scrubbed continuation of a contaminated session. A credential incident never fabricates an experiment outcome, deletes metric history wholesale, resumes partial training, or bypasses explicit Resume after an automatic pause. Mark unfinished containment/rotation, unavailable remote records and external copies honestly; do not claim automatic complete removal.

### 6. Evidence, trade-offs, validation and handoffs

Current primary documentation checked on 2026-11-14 supports the following constraints; the choices above are application policy:

* [Runpod credentials](https://docs.runpod.io/get-started/credentials) documents restricted/read-only permissions and warns that legacy keys can have broader authority. [Vast authentication](https://docs.vast.ai/api-reference/authentication) and [permissions](https://docs.vast.ai/api-reference/permissions) distinguish `instance_read` from lifecycle-capable `instance_write`. Actual account/key permissions must be qualified; a label saying “read only” is not proof.
* [Vast's Docker environment](https://docs.vast.ai/guides/instances/docker-environment) documents `CONTAINER_API_KEY`, Jupyter tokens, lifecycle commands and credential regeneration from instance files/environment. This makes inherited/derivable remote credentials an explicit #54 preflight obligation, beyond stripping `env`. The #39 2FA/session requirement is retained; its linked dedicated 2FA page was inaccessible during this check, so exact current challenge/session mechanics remain a #40 qualification check, not an invented protocol.
* [OpenSSH configuration](https://man.openbsd.org/ssh_config#ForwardAgent) explains that remote users able to access a forwarded agent socket can authenticate with its keys. Hence no agent forwarding; key/host-trust changes remain deliberate trusted actions.
* [Hugging Face token guidance](https://huggingface.co/docs/hub/en/security-tokens) supports app-specific fine-grained read access. Its [environment reference](https://huggingface.co/docs/huggingface_hub/en/package_reference/environment_variables) identifies token/cache locations, implicit authentication and debug cURL logging. Use an isolated fetcher cache/config, explicit intended token use, no `login()`/Git credential persistence, and disabled debug request logging; transfer artifacts without that state.
* [Anthropic secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment) supports isolating credentials from agent environments and restricting filesystem/network authority. This supports the boundary; no SDK option alone proves OS isolation. The completed agent decisions remain the selected routes.

**Trade-offs:** OS-backed encryption and narrow access add unlock/signing/packaging work and require reauthentication when moving projects. Brokered downloads avoid placing account tokens on rented compute but cost local staging/transfer and require a trusted credential-free package. Conservative omission can reduce diagnostic detail; visible gaps retain that limitation. Native Codex recovery retains private potentially sensitive state, while Claude deliberately sacrifices native session resume. Strict isolation can reject an existing instance that would otherwise run training; there is no full-access fallback. Neither storage encryption nor matching proves safety against a compromised privileged host/provider, arbitrary secret encoding, or previously exported data.
