# Spike decision/evidence: desktop stack and persistence (#15)

Date: 2026-11-13. Status: research decision for review, **not an approved product specification or authorization to implement**. Assigned issue: [#15](https://github.com/igrgin/autoresearch-lab/issues/15).

## Decision and scope

Select **Electron, TypeScript, React, Electron Forge with webpack, and SQLite through `better-sqlite3`**. Keep privileged coordination and persistence outside the renderer, using an Electron Node utility process. Use the Git CLI for actual repositories/worktrees. Keep datasets, model files, and bulk activity/log files on the filesystem; store structured history, indexes, transfer references, and recovery bookkeeping in SQLite. Use one application registry database and one history database per project.

This is an engineering choice, not a claim that the agent integrations require TypeScript. Both agents have Python options, and Codex app-server has a language-neutral protocol. TypeScript reduces the number of local implementation languages and lets web UI and host adapters share development tools; protocol definitions remain language-neutral and owned by [#16](https://github.com/igrgin/autoresearch-lab/issues/16).

The [approved concepts brief](../../designs/concepts_brief.md), located through the [design sitemap](../../designs/SITEMAP.md), controls scope. The first complete route remains **Runpod → Codex → external pretrained initialization → one GPU**. The choice must also accommodate Vast.ai, Claude, agent-designed and previous-run initialization, concurrent runs on distinct instances, and multi-GPU execution before full v1 completion. Windows releases remain outside v1; future portability is a cost consideration, not a new release commitment.

No credential policy is selected here: [#17](https://github.com/igrgin/autoresearch-lab/issues/17) owns storage/access/redaction/exposure response. No new lifecycle, evaluation, timeout, or retention policy is introduced. Live owning spikes were read: [Codex #44](https://github.com/igrgin/autoresearch-lab/issues/44), [Claude #49](https://github.com/igrgin/autoresearch-lab/issues/49), [execution #54](https://github.com/igrgin/autoresearch-lab/issues/54), [evaluation #61](https://github.com/igrgin/autoresearch-lab/issues/61), [stopping #67](https://github.com/igrgin/autoresearch-lab/issues/67), [lifecycle #73](https://github.com/igrgin/autoresearch-lab/issues/73), [history/logs #86](https://github.com/igrgin/autoresearch-lab/issues/86), and [model retention #92](https://github.com/igrgin/autoresearch-lab/issues/92). Their unresolved policies remain with them.

These are qualitative engineering judgments against the brief, not benchmark results. All three can support a local database, Git subprocesses, and network adapters. None makes remote work safe merely by running a desktop process.

**Why Electron wins here:** the workload is an integration-heavy research controller with histories, graphs and subprocesses. Its existing Node host avoids adding Rust or Swift plus a separate SDK runtime to the first build. Tauri would be reasonable if measured footprint became a binding constraint, or a Rust implementation team/runtime strategy already existed. SwiftUI would be reasonable if native macOS presentation outweighed portability and adapter reuse. Neither condition is established in this repository. React is a maintainability choice for the history/dashboard UI, not a source-backed performance claim. No RAM, startup or package-size benchmark was run.

Use Forge's webpack/TypeScript route rather than add Vite to the initial toolchain: Forge documents the webpack template and currently labels its Vite support experimental, with possible breaking minor changes. Pin actual tool versions during the authorized build rather than rely on an unversioned scaffold command. [Webpack template](https://www.electronforge.io/templates/typescript-+-webpack-template), [Vite caveat](https://www.electronforge.io/templates/vite-+-typescript).

## Actual agent runtime constraints

**Codex:** official documentation distinguishes a server-side TypeScript SDK (Node 18+) for automating jobs from app-server for rich custom clients. It also documents a Python SDK (Python 3.10+), so a web/TypeScript shell is not mandatory. App-server exposes JSON-RPC messages over default stdio, version-specific schema generation, conversation/thread/turn events and interruption. Its WebSocket transport is explicitly experimental and unsupported. Consequently, budget a real executable host and version-pinned adapter; do not treat Codex as a browser-only HTTP text API or rely on a remote WebSocket listener as the first production transport. Prefer investigating stdio app-server for the rich client in #44; this spike does not settle that integration decision. [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk), [app-server](https://learn.chatgpt.com/docs/app-server).

**Claude:** the Agent SDK is available in TypeScript and Python, and operates a Claude Code binary, rather than merely wrapping the Messages API. Current prerequisites are Node 18.14+ or Python 3.10+. Both SDKs normally bundle a native binary; the TypeScript binary arrives via optional npm dependencies, so omitting optional dependencies can remove it. A separate agent subprocess owns the working directory and on-disk session state. Distinct concurrent sessions need explicit working directories, and remote filesystem/session survival needs a storage strategy. #49 must establish exposed activity, cancellation, model support, authentication and safe recovery for the pinned release. [Overview](https://code.claude.com/docs/en/agent-sdk/overview), [quickstart](https://code.claude.com/docs/en/agent-sdk/quickstart), [hosting](https://code.claude.com/docs/en/agent-sdk/hosting).

These facts favor a Node-capable host but **do not prove SDK compatibility with packaged Electron**. Utility processes provide Node and message ports; subprocess resolution, SDK native binaries, runtime versions, signed helpers and package resources still require a packaged test. Keep executable resources outside ASAR with absolute resolved paths: Electron documents limitations on spawning executables inside the archive. [Utility process](https://www.electronjs.org/docs/latest/api/utility-process), [ASAR limitations](https://www.electronjs.org/docs/latest/tutorial/asar-archives#executing-binaries-inside-asar-archive).

Execution happens on the host where the agent's tools run, unless an explicitly supported remote tool/execution facility is selected. An agent running locally does not automatically edit or supervise the Runpod filesystem. Keep local setup and remote research execution locations explicit in the adapter boundary. #44/#49/#54 must prove the chosen placement and transport. The stack can host local adapters and communicate with a remote worker without shipping Electron/Chromium to GPU machines.

## Component ownership and native exit

This is a deployment/storage allocation; #16 owns logical identities, message shapes, compatibility and ordering. Do not export Electron IPC objects, TypeScript classes, SQLite rows or native process handles as shared integration contracts.

| Component | Responsibility and boundary |
| --- | --- |
| React renderer | Views, forms, charts and read projections. No direct database, Git, filesystem, SDK or provider access. Render captured activity as untrusted content. |
| Preload bridge | Small validated command/query surface between renderer and host; no general shell/SQL or raw IPC passthrough. |
| Electron main | Native windows/menus/dialogs, close/quit coordination, single-controller admission and utility-process health. Keep durable work out of the UI event loop. |
| Node utility process / local coordinator | Sole application writer for open databases; workspace file/Git operations, durable command bookkeeping, ingestion, adapter supervision and queries. Agents do not receive a database connection. Process separation is crash containment, not an agent security sandbox. |
| Provider/agent adapters | Implement #16's language-neutral contracts; discover/connect to existing compute and map integration capabilities/errors. They do not invent lifecycle/evaluation outcomes. |
| Remote execution/safeguard component | Own application-scoped process supervision, bounded work and durable remote evidence even when the desktop is absent. Protocol, implementation language and bounds belong to #54/#67/#73. |

Electron recommends context isolation, disabled renderer Node integration, sandboxing and careful IPC validation. Adopt those host boundaries without choosing the credential policy. Filesystem placement alone cannot keep an arbitrary same-user agent away from protected data; enforceable isolation is a #54/#17 dependency. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security).

For native window close and Cmd+Q, synchronously veto the native event while active work exists, then use one reentrancy-safe coordinator to warn/confirm and request graceful Pause for all active runs. A Cancel keeps the app open. Confirmed exit waits for the agreed pause/persistence result before releasing the veto; use normal quit only after completion. Electron's immediate `app.exit()` bypasses quit hooks and cannot be the graceful-close implementation. Native window close must cover all active runs, including those not on screen; do not merely hide the window and leave research running. [Window close](https://www.electronjs.org/docs/latest/api/browser-window#event-close), [quit and exit](https://www.electronjs.org/docs/latest/api/app#appquit).

That mechanism supports the brief but does not define what to do when pausing fails or a process is force-killed. #73 owns close-failure behavior and control/completion precedence. Force Quit, crash and sleep cannot depend on a final local message; the brief requires the independent remote safeguard, preserved pending outcomes, reconciliation and explicit Resume. Do not release reservations merely because a socket or utility process closed. No provider start/stop/terminate action is added.

## Persistence alternatives and selected boundaries

| Option | Assessment |
| --- | --- |
| JSON settings plus JSONL as the only database | Useful for interchange and sequential activity capture. Recovery, deduplication, indexed graphs, multi-record updates and migrations would require a bespoke storage layer. Reject as the authoritative structured store; this is a complexity judgment, not a claim that transactional file designs are impossible. |
| SQLite (selected) | Embedded local application storage with transactions and indexed queries, no database service to install. One writer at a time is suitable if the coordinator serializes short writes; bulk files stay outside it. [Appropriate uses](https://www.sqlite.org/whentouse.html), [transactions](https://www.sqlite.org/lang_transaction.html). |
| PostgreSQL | Strong server database, but adds a server process, installation and operational lifecycle for a personal local application. No shared multiuser database requirement justifies that cost. [PostgreSQL architecture](https://www.postgresql.org/docs/current/tutorial-arch.html). |
| Browser IndexedDB/localStorage as the primary store | Reject as an ownership choice: recovery and reservation coordination must work independently of renderer/browser session state. It can cache disposable UI preferences; it must not own runs. |

Select explicit SQL migrations and prepared SQL behind a repository interface; no ORM is needed initially. `better-sqlite3` provides transactions and backup support; verify the pinned binding/native payload in the packaged utility process. Electron documents native-module compatibility/rebuild considerations and Forge's integration with rebuilding. Do not assume a successful system-Node install proves packaged compatibility. [Binding API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md), [Electron native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules). Built-in `node:sqlite` is a future simplification candidate, but current Node docs mark it release-candidate stability and availability depends on Electron's embedded Node; do not silently substitute it. [Node SQLite](https://nodejs.org/api/sqlite.html).

Illustrative layout; final names/schema follow #16. Paths below describe future application data, not files added by this spike:

```text
application support/
  registry.sqlite         # project locations, global defaults, reservations/intents
workspace/projects/<project>/
  .git/                   # generated source history and retained tested refs
  dataset/                # copied/moved source files, outside source tracking
  .lab/history.sqlite     # settings snapshots, attempts, results, metrics, recovery
  .lab/activity/          # admitted activity and log segments plus gap metadata
  .lab/artifacts/         # selected model packages and partial transfers
  runs/<run>/             # isolated Git working directories
```

Project history and retained artifacts travel with the project; the registry tracks installation-specific locations and application-wide reservations. Resolve internal file references relative to the project root; store project identity separately from its current path. Runtime application data is Git-ignored. Git holds generated source/configuration and instructions, not datasets, databases, transcripts or model binaries. A project database is authoritative for saved run settings/history; any human-readable settings export is derived, with no second writable source of truth. Global defaults affect newly saved configurations, not existing run snapshots.

Git worktrees share repository data while keeping per-worktree HEAD/index state. Therefore Git mutations need coordination at the repository level; worktree isolation is not full process/security isolation. Keep durable application-owned refs for every tested commit before returning a run branch to accepted code; rejected candidates cannot depend only on a reflog. First internal build may require an installed Git CLI with an actionable preflight, resolved executable path and recorded version. Test that path in a Finder-launched app; do not assume a shell's PATH. Self-contained Git distribution/signing is a separately unproven release-packaging check, not something this research claims to have delivered. [Git worktree documentation](https://git-scm.com/docs/git-worktree).

The history database stores settings snapshots, identifiers, validation/assessment records, metric samples or indexed metric series, outcomes, artifact manifests/references and collection status. Required experiment and whole-run history must remain queryable after weight cleanup. Large log/activity payloads and model weights stay in files to keep database writes and backups manageable. Separate user-only assessment access from agent-facing queries according to the brief; storing both in one trusted database is not itself enforcement. Do not expose the project history directory to candidate tools as a general history source.

Only records admitted under the future #17 policy may enter activity files, SQL, UI or later context. This does not select a sanitizer, secret store or credential delivery mechanism. Keep truncation/collection gaps explicit; #86 owns exact limits and aggregation semantics. #92 owns package contents, source-model dependency protection, retention and low-space policy. Store transfer availability separately from run completion so a completed run with an incomplete local model does not appear fully retrieved.

## Durability, reconciliation and migration consequences

Use WAL on supported local filesystems, foreign keys enabled per connection, short serialized transactions, a bounded busy policy and `synchronous=FULL` for durable records. Assert actual PRAGMA results. WAL permits readers alongside one writer, needs checkpoint management, cannot serve as a shared network-filesystem database, and does not atomically commit across multiple attached databases. Current SQLite documentation also reports a WAL-reset race fixed in **3.51.3+**, with specific earlier backports. Require a verified fixed SQLite build in the selected binding; do not inherit the system SQLite version blindly. Reject unsupported live network/sync-folder operation until tested, and provide a recovery-safe project move/backup path. These are storage constraints, not a narrowing of task/model scope. [SQLite WAL documentation](https://www.sqlite.org/wal.html).

In one project transaction, persist an admitted event with its #16 deduplication identity, update projections and advance the durable ingestion cursor. Acknowledgment must follow commit. On restart, replay/reconcile from persisted evidence rather than fabricate completion or repeat a launch because a reply was lost. Exact acknowledgment/ordering rules belong to #16/#54; this storage choice must support them. Database recovery cannot recover a destroyed instance or prove remote execution stopped.

The registry and project database are **not one atomic unit**. Persist a reservation/operation intent in the global store before dispatch; record the corresponding project transition separately. If either side fails, retain the conservative reservation and reconcile using stable identifiers. Never hold a SQL transaction open across network calls. The detailed states/release rules remain #16/#73's decisions. Git changes and file writes likewise need recoverable intent/completion records, not a fictitious transaction spanning SQL, Git and remote actions.

For artifact/log publication, write to a temporary file, verify required completeness/integrity, publish on the same filesystem, then commit its durable reference. Recover abandoned partial files and references whose files are missing; distinguish missing content from a missing experiment result. Exact integrity/package/cleanup rules remain #86/#92. Filesystem crash durability and atomic publication must be tested on supported volumes; this spike does not assert that rename alone guarantees power-loss safety.

Use numbered, forward migrations with a schema-version record and checksum history, independently for registry and project stores. Before upgrading, stop competing writers, make a consistent backup, apply each transactional SQL migration and version update together, then validate. Reject a newer unknown schema without writing it. A failed migration preserves the prior database and reports failure; do not auto-reset user history. App/remote protocol versions and artifact formats are separate from SQL schema versions. Filesystem transformations need restartable progress and their own backup/rollback handling. Downgrade means deliberate backup restoration, not destructive reverse migrations. SQLite's online backup API supplies a consistent snapshot; copying only a live `.sqlite` file is insufficient as a backup strategy. [Backup API](https://www.sqlite.org/backup.html).

## Smallest authorized first-build path and portability costs

This is a proposed path for the dependent implementation phase; no application code, scaffold, dependencies or CI configuration was created here.

1. Pin a supported Electron/Node, Forge webpack/TypeScript, React and SQLite binding tuple with a lockfile. One application package can contain separate main, preload, renderer and utility entrypoints; avoid a web server, local HTTP backend, cloud database or local Python training install solely for the desktop shell.
2. On macOS CI, install from the lockfile, typecheck/lint, run storage/contract fixture checks, and use Forge `package`/`make` to produce an unsigned internal `.app`/ZIP. Start with an explicit arm64 target, then add x64 compilation and packaged smoke before claiming Intel support; macOS is the first CI platform. Forge separates executable bundle packaging from distributable creation. [Forge lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle).
3. Prove packaged native close/Cancel/Cmd+Q, utility-process startup and database migration/restart with a simulated adapter before live credentials. Then prove the Runpod/Codex/external-pretrained single-GPU route under the owning spike decisions. Preserve full-v1 follow-through rather than calling that route all of v1.
4. Before external distribution, sign and notarize the app and nested helpers/binaries, then verify on a clean Mac. Forge documents Developer ID signing and notarization as distribution steps; unsigned CI packaging is not release proof. Packaging needs the selected agent binary/license and Git dependency strategy checked explicitly. [macOS signing](https://www.electronforge.io/guides/code-signing/code-signing-macos).

Future Windows/Linux support reuses UI, SQL and contract concepts but still costs OS-specific builds/signing/installers, Git/agent binary availability, native binding smoke tests, path/case/Unicode handling, filesystem durability checks, subprocess-tree cancellation, menus/quit/session-end behavior and sandbox verification. Electron's larger runtime and ongoing security updates are accepted maintenance costs; no free portability or automatic safe Windows process termination is promised.

## Validation performed and limits

On 2026-11-13 in the prepared macOS arm64 worktree at baseline `cea79a40b801c6f9fe589a5461bdef5b993e66fc`:

- Fetched the official documentation linked near factual claims. Apple symbol pages initially returned a JavaScript shell; their official Markdown links supplied the actual API text. Some guessed Forge/Apple documentation URLs failed to fetch; corrected official pages were used. No failed GitHub CLI operation occurred during investigation.
- Ran an ephemeral Python SQLite check on SQLite **3.40.1** using a local temporary directory, WAL and FULL synchronization. A child committed an event/projection pair, began another event/projection/DDL/schema-version transaction, signaled readiness, then received SIGKILL. Reopening retained only the committed pair, the original schema version and no inflight table. **PASS**.
- Replayed the committed unique event ID: insertion failed and the projection remained unchanged. **PASS**. Created an online backup; event rows matched and both databases returned `integrity_check=ok`. **PASS**. Temporary files were removed.

This is a storage-primitives sanity check, **not** validation of a production schema, the SQLite WAL race fix, Electron, `better-sqlite3`, multiple database coordination, disk-full behavior, actual power loss, Git packaging, authentication, live agents, Runpod, cancellation or remote supervision. The older Python SQLite is not an acceptable substitute for the fixed release required above. No application tests/build existed to run; no app or GPU work was launched.
